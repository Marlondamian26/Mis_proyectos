# Guía Completa para Desplegar en Render - Backend y Frontend

=======================================================================
INTRODUCCIÓN
=======================================================================

Esta guía describe paso a paso cómo desplegar una aplicación completa en Render,
incluyendo un backend (Node.js/Express) y un frontend (React/Vite o Create React App).
El objetivo es proporcionar un documento autocontenido que permita configura
el despliegue desde cero sin necesidad de referencias externas.

La visión general del flujo es:
1. Preparar el código local con la estructura adecuada
2. Crear servicios en Render (backend web + frontend estático)
3. Configurar variables de entorno y conecta la base de datos si aplica
4. Desplegar automáticamente vía GitHub
5. Verificar que todo funciona correctamente

=======================================================================
SECCIÓN 1: REQUISITOS PREVIOS Y VERIFICACIÓN
=======================================================================

# Requisitos de cuenta GitHub
# Tener una cuenta en GitHub (github.com) y un repositorio con el código.
# El repositorio puede contener solo el frontend, solo el backend, o ambos.

# Permisos necesarios
# En GitHub, asegurar que Render tenga acceso al repositorio:
# - Ir a Settings → Applications → OAuth Apps
# - Verificar que Render esté autorizado
# - Alternatively, al crear el servicio en Render se puede autorizar el acceso

# Plan gratuito de Render
# Render ofrece un plan Free con las siguientes limitaciones:
# - Backend: 750 horas/mes (se desactiva después de 15 min de inactividad)
# - Frontend estático: 100 GB/mes de ancho de banda
# - Base de datos PostgreSQL: 1 base de datos gratuita (se apaga tras 90 días)
# - Los servicios free se suspenden después de不 inactivity, no son para producción 24/7

# Herramientas necesarias en本地
# - Node.js 18+ (recomendado LTS)
# - npm o yarn (gestor de paquetes)
# - Git (para versionar y pushes a GitHub)
# - Acceso a terminal/línea de comandos
# - Navegador web moderno para acceder a Render Dashboard

# Verificar instalación de Node.js
node --version
# Debería mostrar versión 18.x o superior

# Verificar npm
npm --version
# Debería mostrar versión 9.x o superior

# Instalar herramienta CLI de Render (opcional, para ver logs)
# npm install -g @render/cli
# render --version

SECCIÓN 2: ESTRUCTURA RECOMENDADA DEL REPOSITORIO
=======================================================================

# ENFOQUE A: Monorepo (backend + frontend en un repositorio)
# Ventajas:
# - Un solo repositorio para gestionar
# - Un solo push para actualizar ambos servicios
# - Más simple para proyectos pequeños/medianos
# Desventajas:
# - Render requiere configurar Root Directory para cada servicio
# - Los builds están en directorios separados

# Estructura de monorepo recomendada:
# /mis-proyectos/
# ├── backend/           # Código del backend
# │   ├── src/
# │   ├── package.json
# │   ├── index.js      # Punto de entrada (app.js/main.js)
# │   └── .env.example # Plantilla de variables de entorno
# ├── frontend/         # Código del frontend (Vite o CRA)
# │   ├── src/
# │   ├── package.json
# │   ├── vite.config.js  # o react-scripts/config
# │   └── .env.example
# ├── render.yaml       # (Opcional) Configuración declarativa
# └── README.md

# ENFOQUE B: Repositorios separados
# Ventajas:
# - Total independencia entre servicios
# - Simpler de configurar en Render (sin Root Directory)
# - Diferentes ramas para CI/CD si se desea
# Desventajas:
# - Dos repositorios que mantener
# - Más complejo de sincronizar

# Estructura de repos separados:
# Repo 1: mi-backend
# ├── src/
# ├── package.json
# └── index.js
#
# Repo 2: mi-frontend
# ├── src/
# ├── package.json
# └── vite.config.js

# CRITERIOS PARA ELEGIR:
# - Monorepo si: proyecto personal, equipo pequeño, desarrollo rápido
# - Repos separados si: equipo grande, despliegues independientes, proyectos muy distintos

# Archivos clave en backend (paquete.json):

# ====================================================================

# Este es un ejemplo completo de render.yaml con dos servicios:
# - api-backend: backend tipo web (Node.js/Express)
# - app-frontend: frontend estático (React)

# ====================================================================
# SERVICIO 1: BACKEND (API)
# ====================================================================

# Representación en formato YAML servicios-normalizado:
# services:
#   - name: api-backend               # Nombre del servicio en Render Dashboard
#     type: web                   # Tipo: web (servidor HTTP persistente)
#     env: node                  # Entorno: node (Node.js)
#     region: oregon             # Región recomendada para latencia
#     branch: main             # Rama git que activa despliegues automáticos
#     plan: free               # Plan: free (u hourly para producción)
#     buildCommand: npm ci    # Instala dependencias reproduciblemente
#     startCommand: npm start # Inicia el servidor (debe ser comando que no regrese)
#     envVars:
#       - key: NODE_ENV
#         value: production
#       - key: DATABASE_URL
#         sync: false          # No sincronizar entre despliegues
#       - key: SECRET_KEY_BASE
#         sync: false
#           # sync: false significa que el valor no se muestra en UI
#           # Es para valores sensibles que se configuran manualmente o vía CLI
#     # Vars de entorno para el frontend (opcional, si el backend provee datos públicos)
#     # En este caso las agregamos aquí para que estén disponibles

# ====================================================================
# SERVICIO 2: FRONTEND (React estático)
# ====================================================================

# Representación en formato YAML servicios-normalizado:
# services:
#   - name: app-frontend          # Nombre del servicio
#     type: static             # Tipo: static (sitio web estático)
#     env: node              # Entorno para construir
#     region: oregon         # Misma región que el backend
#     branch: main          # Rama que activa despliegues
#     plan: free           # Plan gratuito
#     buildCommand: npm ci && npm run build
#                          # Primero instala, luego build (genera /dist)
#     staticPublishPath: dist
#                          # Directorio donde está el HTML/CSS/JS construido
#                          # Para Vite: dist | Para CRA: build
#     envVars:
#       - key: VITE_API_URL
#         value: https://api-backend-xxxx.onrender.com/api
#                          # URL del backend (se configura tras primer deploy)
#         # IMPORTANTE: El frontend necesita saber la API del backend
#         # En código: import.meta.env.VITE_API_URL
#     # Dependencies permite conexion between servicios
#     # (Render conecta automáticamente si se configuran correctamente)
#     dependsOn:
#       - serviceName: api-backend
#                          # Indica que este servicio depende del backend
#                          # Si el backend no está, el frontend esperará

# ====================================================================
# OPCIÓN A: USAR RENDER.YAML (Infraestructura como Código)
# ====================================================================

# Ventajas de usar render.yaml:
# - Configuración versionada junto con el código
# - Reproducible y documentado
# - Un solo push actualiza toda la infraestructura
# - Reversión fácil si hay problemas

# Pasos para usar render.yaml:
# 1. Crear el archivo render.yaml en la raíz del repositorio
# 2. Asegurar que el código cumple con los requisitos:
#    - Backend: package.json con scripts de "start" y "build" si aplica
#    - Frontend: package.json con script de "build" y genera directorio correct
# 3. Hacer push a la rama configurada (ejecutivo: main)
# 4. Render detectará el archivo y creará los servicios automáticamente
# 5. La primera vez, configurar variables sensibles manualmente

# Para actualizar tras modificar render.yaml:
git add render.yaml
git commit -m "Update render.yaml"
git push

# Render también lee el archivo en cada despliegue y reconcilia cambios.

# ====================================================================
# OPCIÓN B: CONFIGURAR DESDE LA UI DE RENDER
# ====================================================================

# Pasos para crear backend web:
# 1. Ir a https://dashboard.render.com
# 2. Click "New" → "Web Service"
# 3. Conectar repositorio GitHub (autorizar si es necesario)
# 4. Seleccionar repo y rama
# 5. Configurar:
#    - Name: api-backend
#    - Region: Oregon u Ohio
#    - Environment: Node
#    - Build Command: npm ci
#    - Start Command: npm start
#    - Plan: Free
# 6. Click "Create Web Service"

# 1. Click "New" → "Static Site"
# 2. Conectar mismo repositorio GitHub
# 3. Configurar:
#    - Name: app-frontend
#    - Region: igual que el backend
#    - Branch: main
#    - Build Command: npm ci && npm run build
#    - Publish directory: dist (o "build" para CRA)
# 6. Click "Create Static Site"

SECCIÓN 5: FLUJO DE DESPLIEGUE Y AUTOMATIZACIÓN

# ====================================================================
# CONECTAR EL REPOSITORIO
# ====================================================================

# Cuando creas un servicio en Render, se conecta automáticamente el repositorio.
# El flujo típico es:
# 1. Crear servicio en Render (via UI o YAML)
# 2.Autorizar acceso a GitHub si es la primera vez
# 3. Seleccionar repositorio y rama (main, master, develop, etc.)
# 4. Listo: cada push a esa rama dispara un nuevo despliegue

# ====================================================================
# RAMAS Y DESPLIEGUE AUTOMÁTICO
# ====================================================================

# Por defecto, solo la rama configurada activa despliegues (ejecutivo: main).
# Se puede cambiar la rama en la configuración del servicio.
# 
# Para activar múltiples ramas:
# - En UI: Settings → Branch Settings
# - En YAML: agregar "pullRequests: enabled" para PRsautomáticos

# ====================================================================
# PREVIEW DEPLOYMENTS (Despliegues de Vista Previa)
# ====================================================================

# Los Preview Deployments crean URLs temporales para pull requests.
# Son útiles para revisar cambios antes de merger a main.
# 
# Para habilitar:
# 1. Ir a Settings del servicio
# 2. Buscar "Preview Deployments"
# 3. Habilitar para pull requests automatizados
# 
# Cada PR recibe una URL tipo: https://servicio-yyy-pr-zzz.onrender.com

# ====================================================================
# NOTIFICACIONES DE DESPLIEGUE
# ====================================================================

# Configurar alertas para saber cuando falla un despliegue:
# 1. Settings → Deployments → "Notify on: Failure" o "Notify on: All Deploys"
# 
# Para integrate con Slack, Discord, etc.:
# - En Settings → Webhooks
# - Agregar webhook URL externo

# ====================================================================
# FORZAR UN DESPLIEGUE
# ====================================================================

# Para realizar un despliegue manual:
# 1. En Dashboard: Click "Manual Deploy" → "Deploy latest commit"
# 2. O especificar un commit específico
# 
# CLI (con @render/cli):
# render deploy --service-id <service-id>

# ====================================================================
# VERIFICAR QUE EL NUEVO BUILD FUNCIONA
# ====================================================================

# Pasos post-despliegue:
# 1. Ir a la URL asignada (https://servicio.onrender.com)
# 2. Verificar endpoints del backend con /api/endpoint
# 3. Verificar el frontend carga correctamente
# 4. Revisar logs en la pestaña "Logs" del Dashboard
# 5. Si hay errores, revisar los logs detallados

# ====================================================================

=======================================================================

# ====================================================================
# DOMINIO PERSONALIZADO EN RENDER
# ========================================================================

# Render permite dominio gratuito con SSL para dominios propios.
# 
# Pasos para agregar dominio:
# 1. Ir al servicio → Settings → "Custom Domains"
# 2. Agregar dominio (ejecutivo: midominio.com)
# 3. Render proporcionará registros DNS para configurar:
#    - Type: CNAME o A
#    - Name: www o @
#    - Value: tu-servicio.onrender.com
# 
# Configurar DNS en proveedor del dominio (GoDaddy, Namecheap, etc.):
# - Agregar registro CNAME con el valor proporcionado
# - Para root domain (@), posible que se requiera registro A (no CNAME)

# ====================================================================
# CERTIFICADOS TLS/SSL
# ========================================================================

# Render proporciona SSL automático y gratuito:
# - Los certificados se generan automáticamente al configura dominio
# - TLS 1.2+ soporta
# - Certificados de Let's Encrypt (autoridad reconocida)
# - Renovación automática cada 80 días
# 
# Para verificar HTTPS:
# - visitar https://midominio.com
# - El candado en el navegador confirma certificado válido

# ====================================================================

SECCIÓN 11: NOTAS DE COSTOS Y BUENAS PRÁCTICAS
=======================================================================

# ====================================================================
# RECOMENDACIONES PARA MINIMIZAR COSTOS
# ========================================================================

# Plan Free de Render tiene límites importantes. Para minimiza gastos:

# - Mantener solo servicios necesarios
# - No crear recursos adicionales innecesarios
# - Base de datos gratuita tiene límite de 90 días (usar o_upgrade)
# - Los servicios free se suspenden tras 5 minutos (backend) / 90 días (front-end)

# ====================================================================
# PRÁCTICAS PARA PRODUCCIÓN
# ========================================================================

# Cuando necesitas disponibilidad continua:

# - Actualizar a plan de pago (desde $7/月 para backend)
# -.backend: $25/月 para 1 instancia always-on
# - Base de datos PostgreSQL: $7/月 para instancia start
# - Frontend estático: BW/GB transferred instead, usually free tier enough

# ====================================================================
# QUÉ MONITOREAR
# ========================================================================

# Métricas importantes:
# - Availability (Estado Alive vs. Suspended/Error)
# - Latencia de respuestas (endpoints)
# - Uso de memoria y CPU
# - Errores en logs
# - Ancho de banda del frontend
# 
# Establecer alertas:
# - Para errores frecuentes en logs
# - Para estado diferente a "Live"

# ====================================================================
# ENTORNOS DE STAGING
# ========================================================================

# Para probar cambios antes de producción:
# - Crear rama "staging" en repositorio
# - Crear servicios separados en Render vinculados a staging
# - Probar en URLs de staging
# - Luego hacer merge a main y desplegar a producción

# ====================================================================
# EVITAR INTERRUPCIONES INNECESARIAS
# ========================================================================

# Buenas prácticas:
# - No hacer deploys constantes a servicios free (puede agotar horas)
# - Probar localmente antes de hacer push a producción
# - Usar ramas feature para desarrollo y PRs para review
# - Mantener código estable antes de merge a main
# - Revisar siempre los logs después de un deploy

# ====================================================================
# SEGURIDAD EN PRODUCCIÓN
# ========================================================================

# Recomendaciones:
# - Usar HTTPS siempre
# - No exponer credenciales en código
# - Rotar claves periódicamente
# - Usar los minimum permissions necesarios
# - Habilitar solo los endpoints necesarios
# - Implementar rate limiting si hay riesgo de ataques
# - Mantener dependencias actualizadas (cuidado con breaking changes)

SECCIÓN 12: MANEJO DE EXCEPCIONES Y SOLUCIONES DE PROBLEMAS
=======================================================================

# ====================================================================
# ERRORES DE CONSTRUCCIÓN (BUILD ERRORS)
# ========================================================================

# Error: "npm error: Cannot find module"
# Causa: Dependencia faltante en package.json
# Solución: Verificar que todas las dependencias están en dependencies/devDependencies
# 
# Error: "Node version mismatch"
# Causa: Versión de Node incompatible con código
# Solución: Especificar "engines" en package.json:
# "engines": { "node": ">=18.0.0" }
# 
# Error: "Module not found" en tiempo de ejecución
# Causa: Falta dependency o error de imports
# Solución: Revisar logs y verificar imports
# 
# Error: "Port already in use"
# Causa: Puerto ocupado o aplicación no libera puerto
# Solución: Usar process.env.PORT y verificar configuración de puerto

# ====================================================================
# ERRORES DE VARIABLES DE ENTORNO
# ========================================================================

# Error: "undefined is not a function" relacionado con variables
# Causa: Variable de entorno no está definida
# Solución: Verificar que está configurada en Dashboard
# 
# Error: "Cannot read property of undefined"
# Causa: process.env.NOMBRE es undefined
# Solución: Proporcionar valor por defecto:
# const valor = process.env.MI_VAR || 'valor-por-defecto'

# ====================================================================
# ERRORES DE RED
# ========================================================================

# Error: "ETIMEDOUT" o timeout
# Causa: servicio no responde o está caído
# Solución:
# - Verificar estado del servicio en Dashboard
# - Revisar logs para errores
# - Si es servicio free, puede estar suspendido

# Error: "ECONNREFUSED"
# Causa: El servidor rechaza conexión
# Solución: Verificar que el servicio está escuchando correctamente

# ====================================================================
# ERRORES DE BASE DE DATOS
# ========================================================================

# Error: "connection refused"
# Causa: Base de datos no está disponible o credenciales incorrectas
# Solución: Verificar DATABASE_URL y estado de la base de datos
# 
# Error: "relation does not exist"
# Causa: Tablas no creadas (falta migrate)
# Solución: Ejecutar migraciones
# 
# Error: "password authentication failed"
# Causa: Credenciales incorrectas en DATABASE_URL
# Solución: Verificar usuario y contraseña en la URL

# ====================================================================
# ERRORES CORS
# ========================================================================

# Error: "Access-Control-Allow-Origin"
# Causa: Backend no permite el origen del frontend
# Solución: Configurar CORS en backend:
const cors = require('cors')
app.use(cors({
  origin: 'https://app-frontend.onrender.com'
}))

# O permitir todos (para desarrollo):
app.use(cors())

# ====================================================================
# ERRORES DEL FRONTEND ESTÁTICO
# ========================================================================

# Error: blank page o "Cannot GET /"
# Causa: staticPublishPath incorrecto o build falló
# Solución:
# - Verificar que el build genera el directorio correcto (dist/build)
# - Verificar que index.html existe en ese directorio
# - Revisar logs de build
# 
# Error: 404 en assets
# Causa: Rutas de assets incorrectas
# Solución:
# - Configurar base en vite.config.js:
base: '/'
# - Verificar que los paths son relativos o absolutos desde raíz

RESUMEN FINAL
=======================================================================

Esta guía proporciona todo lo necesario para desplegar en Render:
1. Preparar el código con estructura correcta
2. Configurar render.yaml o servicios desde UI
3. Agregar variables de entorno (incluyendo DATABASE_URL si aplica)
4. Conectar dominio propio si se desea
5. Verificar funcionamiento post-despliegue
6. Monitorear y mantener

Para adaptarlo a otras pilas similares:
- Python/Flask/Django: Cambiar env a python, buildCommand a pip install
- Go: Cambiar env a go, ajustar comandos de build
- Ruby on Rails: Cambiar env a ruby, ajustar migrate
- Otros frameworks: Ajustar buildCommand y startCommand según documentación

# Copia el siguiente ejemplo y adáptalo a tu proyecto:

# # ====================================================================
# # SERVICIO 1: BACKEND (Node.js/Express)
# # ====================================================================
# services:
#   - name: api-backend
#     # Nombre único del servicio en Render
#     type: web
#     # Tipo: web para servidor HTTP persistente
#     env: node
#     # Entorno de ejecución
#     region: oregon
#     # Región del datacenter (oregon, ohio, frankfurt, singapore)
#     branch: main
#     # Rama de Git que activa despliegues automáticos
#     plan: free
#     # Plan de precios: free o hourly
#     buildCommand: npm ci
#     # Comando para instalar dependencias de forma reproducible
#     # Equivalente a npm install pero más limpio y consistente
#     startCommand: npm start
#     # Comando para iniciar el servidor.
#     # Debe iniciar el servidor HTTP que escuche en process.env.PORT
#     # En package.json típicamente: "node index.js" o "node server.js"
#     envVars:
#       - key: NODE_ENV
#         value: production
#         # Modo de ejecución: development o production
#       - key: PORT
#         value: 3000
#         # Puerto del servidor (Render reemplazará con el suyo)
#       - key: DATABASE_URL
#         sync: false
#         # URL de PostgreSQL.
#         # sync:false evita que se muestre en Dashboard.
#         # Se configura manualmente en la UI o vía CLI.
#       - key: SECRET_KEY_BASE
#         sync: false
#         # Clave secreta para sesiones/tokens.
#         # Generar con: openssl rand -base64 32
# 
# # ====================================================================
# # SERVICIO 2: FRONTEND (React/Vite)
# # ====================================================================
#   - name: app-frontend
#     # Nombre del servicio de frontend
#     type: static
#     # Tipo: static para sitio web estático (HTML/CSS/JS)
#     env: node
#     # Entorno de build (Node.js para construir el frontend)
#     region: oregon
#     # Misma región que el backend para menor latencia
#     branch: main
#     # Rama que activa despliegues automáticos
#     plan: free
#     # Plan gratuito (100 GB/mes de transferencia)
#     buildCommand: npm ci && npm run build
#     # Primero instala dependencias, luego construye para producción
#     # Genera directorio: dist (para Vite) o build (para CRA)
#     staticPublishPath: dist
#     # Directorio publicado después del build.
#     # Para Vite: dist | Para Create React App: build | Para Next.js: .next
#     envVars:
#       - key: VITE_API_URL
#         value: https://tu-backend.onrender.com/api
#         # IMPORTANTE:URL del backend que el frontend usa para chiamar APIs.
#         # Reemplaza "tu-backend" con el nombre real después de crear servicios.

# ====================================================================
# NOTAS SOBRE ESTE EJEMPLO:
# ====================================================================
# - Después de crear los servicios la primera vez, ajustar VITE_API_URL.
# - Las claves con sync:false se configuran manualmente en Dashboard.
# - region: oregon ofrece buen rendimiento para la mayoría de ubicaciones.
# - Para producción, cambiar plan:free a plan:hourly con los recursos necesarios.
